## 2. App level — v1 spec (REQUIREMENTS.md)

**69 of 71 functional requirements implemented.** The running system more than
satisfies its own v1 specification. The two FRs the spec flags as gaps are
both "deferred to v2" items — and both are further along than the spec says:

- **FR-4.3 (automated event ingest + recurring events)** — *largely built,
  shipped dark.* A recurring-event model exists and is tested
  (`src/lib/events/recurrence.ts`, `rrule-expand.ts`, portal repeat controls),
  and an events-ingest pipeline with three adapters runs hourly via Render
  cron. The unified authoritative calendar sits behind the `unified-calendar`
  flag (default OFF, reserved for the E15 cutover). What's genuinely missing:
  recurrence expansion on public surfaces while the flag is off, and
  recurrence controls in the nonprofit editor.
- **FR-15.5 (analytics v2: time-series, JLARC-aligned export, bot filtering,
  k-anonymity)** — *still open*, tracked under the analytics epic below.

## 4. App level — docs drift (both directions)

The planning and architecture docs have fallen behind the code. This matters
because the docs are specified as the rebuild-from-scratch source of truth.

**Code ahead of docs** (docs say missing, actually built): PWA/service worker
(still called "the gating dependency" by the epic notes — it isn't anymore);
recurring-event model; events-ingest pipeline (3 adapters + hourly cron);
Cloudflare R2 image backend; kiosk route group + kiosk analytics; Sentry;
`/line` SR-104 lander + offline basemap tiles; GitHub-issue "request permanent
change" flow; 4 Render crons + staging service. ARCHITECTURE.md still
describes the Render persistent disk and "no automated tests"; SDD counts 40
API routes / 33 pages vs. the actual 66 / ~70.

**Docs ahead of code** (docs imply built, actually absent): GBP/Meta/Apple
syndication adapters (zero adapter code — `/portal/syndicate` is an honest
copy-paste checklist); public directory page (store exists, no public
surface); jobs board; native member store/join (E16/E19); paid ticketing.

**Also:** the busyness forecast is fully built but ships dark (prediction
flag defaults OFF, so `/ferry/plan` 404s publicly) while its observation
crons collect data regardless — that's by design, but two forecast-scoring
bugs found in the code review (mid-fill snapshots graded as ground truth)
mean **the accuracy gate itself is currently measuring the wrong thing** and
must be fixed before the backtest verdict can be trusted.

## 7. Bottom line

The **platform layer the coalition asked to build on is real and healthy** —
live ferry integration, hours engine, portals with moderation and audit,
privacy-first analytics, maps CMS, PWA shell, CI. The v1 spec is essentially
closed. But the **coalition's 13 epics are, on average, ~24% done**, and the
five P0 Phase-1 epics — the "cheapest, highest-trust wins" — average ~40%.
The bulk of remaining work is well-scoped enhancement on top of proven
seams, with 73 concrete work items catalogued in
[COMPLETION-PLAN.md](COMPLETION-PLAN.md). Three external clocks (GBP API
access, LTAC pre-clearance, Resend production config) and one measurement fix
(forecast backtest) should start now because calendar time, not dev time, is
their constraint.
